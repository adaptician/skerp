# AB#1469 PR 728 review feedback

## What changed

- Four active threads. None changes an acceptance criterion of AB#1466-AB#1470, so none is routed to a
  new work item.
- **Thread 4277 (fix):** the API is versioned with `Asp.Versioning.Http` instead of a hand-written `/api/v1`
  prefix. `ApiV1.MapApiV1` builds a version set (1.0, reported) and maps the group at
  `/api/v{version:apiVersion}`; `AddApiVersioning` sets 1.0 as the default and reads the version from the URL
  segment (api.md → Versioning). The feature gate is untouched: `RequireFeature` metadata and
  `UseFeatureGates` still answer 404 while `Feature_PurchaseOrders` is off, including for `/api/v1.0/...`.
- `Asp.Versioning.Mvc.ApiExplorer` is added too: the Http package's own analyser (AV0021) fails the build
  without it once Swagger is registered. It keeps the Swagger document named `v1` with `/api/v1/...` paths.
- The unknown-route fallback now matches `/api/{**path}`, so `v1`, `v1.0` and `v2` all answer the 404
  Result body; `ApiV1.Prefix` had no other consumer and is removed.
- `ApiVersioningTests`: v1 and v1.0 succeed and report `api-supported-versions: 1.0`; unknown routes under
  v1.0 and v2, and an unsupported version of a real route, answer the 404 Result body; a toggled-off group
  answers 404 on a `v1.0` URL; Swagger paths carry no `{version}` placeholder.
- Functional impact re-check (the route group is shared by every endpoint): the 185 unit and 104
  integration tests pass, including the purchase-order, customer, product, feature, toggle-off and Swagger
  tests; the client's `/api/v1` URLs are unchanged. New side effect: every `/api` response carries an
  `api-supported-versions: 1.0` header.
- conformance-review run on this diff: gate 16/16; no blocking findings after the fallback fix below.
- **Thread 4278 (answer only):** no code change; the answer is in the PR reply.
- **Thread 4279 (first answer only, then a fix on the reviewer's go-ahead):** `EditPurchaseOrderCommandHandler`
  splits the request into existing and new lines, resolves the new ones, and concatenates the two revision
  lists: no Queue, no ternary. The `UnknownLineItem` guard stays, with the comment "Id received as existing but
  not matched to lines from db". `LineItemProductResolver` gets the same shape (existing-product lines and
  new-product lines, the new ones paired by `Zip`). New `LineItemProductResolverTests` check each line keeps its
  own product, quantity and price in a mixed request and that nothing is created when a product is unknown.
- **Proxy check (asked for in the same request):** `client/proxy.conf.json` (`/api` to `http://localhost:5000`)
  is still correct and needs no change: the port matches `launchSettings.json`, `.claude/launch.json` and the
  docs. Verified with both servers running: through port 4200, `/api/v1/features` and `/api/v1.0/features`
  answer 200 with `api-supported-versions: 1.0`; `/api/v2/...` and an unknown `/api/v1/...` route answer the
  404 Result body; the Purchase orders page loaded 30 seeded orders (`POST /api/v1/purchase-orders/list` 200,
  no console errors). `.build/config/env-variables.md` and `.build/development/development-environment.md`
  now say the proxy carries every API version, that `/swagger`, `/health` and `/alive` are not proxied, and that
  a pre-review `skerp.db` must be deleted.
- **Thread 4276 (fix):** every `DateTimeOffset`, including the `MinimumAudit` columns and
  `PurchaseOrderStatusChange.ChangedAt`, is stored as fixed-width UTC ISO 8601 text
  (`YYYY-MM-DDThh:mm:ss.sssZ`) instead of UTC ticks (`SqliteConventions.UtcIso8601Converter`). Fixed-width UTC
  text still sorts chronologically, so list ordering and the created-date range filter are unchanged.
  Precision drops from 100ns to milliseconds, as the reviewer specified. The columns come from
  `AddPurchaseOrders`, a human-owned committed migration, so the human approved in chat regenerating it
  in place (migration, Designer and model snapshot). Done with `dotnet ef migrations remove --force` then
  `add AddPurchaseOrders`; the only differences are `INTEGER` to `TEXT` on the timestamp columns.
- New test `Audit_StoresTimestampsAsUtcIso8601Text` reads the raw column with SQL: type `text`, a UTC
  value, and a non-UTC clock instant normalised to UTC.
- Functional impact re-check (the converter covers every timestamp): the purchase-order list ordering and
  range-filter tests, the audit interceptor tests (non-UTC parameter still compares the same instant) and the
  full suite pass; the API still returns ISO 8601 in JSON.

## What surprised you

- `/health` answered 200 on port 4200, but that is the Angular SPA fallback page, not the API: the proxy only
  carries `/api`. Documented rather than widened, since nothing in the client calls those paths.
- An unsupported version (`/api/v2/...`) answers 404, not the 400 `UnsupportedApiVersion` the library
  documents, so it does not reveal that a gated endpoint exists. Recorded in a test.
- The old fallback only matched `/api/v1/...`; once `v1.0` became a valid URL, `/api/v1.0/<unknown>` answered
  an empty 404. Found by a test written to probe it, fixed by widening the fallback.
- `ef migrations add` stamps a new id, so the regenerated migration is `20261025131942_AddPurchaseOrders`,
  not the original `20261023070746`; I left the tool's output untouched, as the standards forbid
  hand-editing migrations.
- `WithFeatureGate` does exist in `Microsoft.FeatureManagement.AspNetCore` 4.8.0 (it adds a
  `FeatureGateEndpointFilter`). The AB#1466 conformance review had already replaced a hand-written
  endpoint filter with middleware, for the same reason; no entry records `WithFeatureGate` being
  evaluated by name.

## What you assumed

- No environment has applied the old `AddPurchaseOrders` (the human's word, not checked): ledger entry

- `Asp.Versioning.*` 10.2.0 is acceptable as a pair of new dependencies (MIT licence). The reviewer named only
