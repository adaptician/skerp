name: plan-epic
description: Decompose an Epic's human-authored description into Features, and each Feature into User Stories and Spikes, creating the backlog in ADO plus an Epic overview and one Feature-level plan per Feature under .agents/specs/epics/<epic-slug>/. Use when asked to plan an Epic, break a multi-feature requirement into backlog items, or before authorising a new Feature under an existing Epic. Does not plan individual User Stories or Spikes — hand off to plan-work-item for that.
---

Turn an Epic's stated outcome into a complete, ordered backlog: the Features it needs, and the User
Stories/Spikes each Feature needs. **This skill stops at the backlog.** It never plans a Milestone,
never writes a spec, and never estimates below the Feature/Story/Spike level — that is
[`plan-work-item`](../plan-work-item/SKILL.md)'s job, once an item reaches the front of the sequence.

> **Draft status.** This skill is new and untested against real Epics. Treat every output as a
> proposal to walk through with a human, not a finished plan, until it has run against several
> practice Epics in ADO and the process is confirmed smooth.

> **Not a revival.** An earlier skill with this same name existed in this framework's history and was
> retired — it authored a six-file-per-epic documentation set (`overview.md`, `roadmap.md`,
> `progress.md`, `certainty-map.md`, `demo-feature-inventory.md`, `architecture.md`) that reached
> 8,000+ lines with no mechanical enforcement behind any of it, and was abandoned for six of its seven
> epics. **This skill produces exactly two kinds of file — one Epic overview, one plan per Feature —
> and creates ADO backlog items. Nothing else.** If you find yourself wanting a roadmap, a certainty
> map, or a progress tracker alongside them, that is the retired shape creeping back.

## 1. Read the Epic, not a plan of your own invention

Read the Epic's `Description` and `Acceptance Criteria` from ADO. A human may have written these
directly, or they may have been generated by [`plan-deliverable`](../plan-deliverable/SKILL.md) from a
Deliverable-level interview — either way, they may link to files in the repository; read every linked
file before decomposing anything. Hierarchy and field reference names:
[`.agents/context/azure-devops.md`](../../context/azure-devops.md).

**Check for a Deliverable README first.** If this Epic's parent Deliverable has one at
`.agents/specs/deliverables/<deliverable-slug>/README.md`, read it before decomposing — it is the vision
this Epic's Feature split must serve (target audience, monetisation, budget and architecture constraints,
what is non-negotiable versus flexible). Its absence is not a blocker; `plan-deliverable` is a recent
addition and most existing Epics predate it.

An Epic's description will usually cover **more than one Feature** without saying so explicitly. For
example: *"Add user management and role-based access control to the system. This should set the
precedent for all permissions and authorisation control for the system"* is one paragraph describing
at least three Features (user management, a permission catalogue, role management) plus supporting
capabilities (linking roles to users, login and registration). Finding that seam is this skill's main
job.

**An Epic-level or Feature-level `Analysis` item may already exist** with research relevant to this
decomposition — check for one under the Epic and read it if present. Analysis is informational, never
a prerequisite: proceed with decomposition whether or not one exists.

## 2. Decompose into Features

Distil the description into the smallest set of Features that are each independently deliverable —
"one capability, one toggle," per `azure-devops.md`. For the user-management example above, that
might be `User Management`, `Granular Permissions`, `Role Management`. Getting this split right matters
more than getting it fast: a Feature that is really two capabilities forces an artificial toggle later,
and a Feature that is too thin creates coordination overhead between Features that always ship together.

For each Feature, decompose further into the **User Stories and Spikes** that outline what needs to be
built — enough to give a complete picture of the work the Epic requires, not a detailed plan of any one
item. If a capability's build risk is unknown rather than its shape, that unit is a Spike, not a Story.

**This is initial planning only.** Do not plan Milestones, do not write a spec, and do not hunt for
untested assumptions the way `plan-work-item` does — that gate belongs to per-item planning, once an
item is picked up.

> **A Feature that integrates with a third party always opens with an Analysis, before any Spike or
> Story.** Reviewing the provider's documentation and planning the integration is what actually produces
> answers a Spike would otherwise have to guess at cold — most importantly, how the provider identifies
> the entity being integrated (e.g. how it maps to a local user), and what shape its data takes. That
> Analysis is also what a mock-provider Story is built against: you need to know what you're building
> before you build it. Sequence such a Feature as **Analysis → build the mock provider (and, separately,
> the live client) → *then*, if the mock/live switching mechanism itself is a genuine unknown, a Spike
> proving the swap** — proving two things can be swapped requires at least one of them to exist first.
> Do not open a third-party integration Feature with a Spike that only restates a question the provider's
> own documentation already answers; that is Analysis work wearing a Spike's clothing.

## 3. Create the backlog in ADO

For every Feature, User Story and Spike this decomposition produces:

- Create the work item under the correct parent (Feature under the Epic; User Story/Spike under the
  Feature), per the hierarchy in `azure-devops.md`.
- Set `Description` to the portion of the Epic's overall scope this specific item covers — not the
  whole Epic's description restated, and not empty.
- Set `Acceptance Criteria` — observable from outside the system, Given/When/Then form, per
  [`.agents/specs/README.md`](../../specs/README.md).
- Set the slug field for that level (`Custom.FeatureSlug` on Features, `Custom.PrimarySlug` on
  User Stories/Spikes).
- **On every Analysis, Design, User Story and Spike this skill creates** (not on Features or the
  Epic itself), set an estimate in **two** fields: `Custom.QuotationPoints` and
  `Microsoft.VSTS.Scheduling.StoryPoints`. **This is the only time an agent may set
  `Quotation Points`.** Later re-planning (by this skill on a re-run, or by `plan-work-item`) may
  revise `Story Points` freely but must never touch `Quotation Points` again — a human revises a quote
  directly in ADO if one is ever needed.

**Surprises found while later planning an individual Story or Spike** (in `plan-work-item`) that need
a new work item belong under this same Epic — they are this skill's concern only insofar as the
relevant Feature's plan (§4) should stay current when that happens; the item creation itself is
`plan-work-item`'s.

## 4. Write the Epic overview and one plan per Feature

Two kinds of file, both **generated once and updated on re-runs** — never duplicated into ADO, only
referenced from it:

- **`.agents/specs/epics/<epic-slug>/README.md`** — short. The Epic's outcome in a few sentences, and a
  list of its Features each linking to its own plan below.
- **`.agents/specs/epics/<epic-slug>/features/<feature-slug>/README.md`** — one per Feature. **This is
  a Feature-level plan, not an implementation specification** — each User Story or Spike gets its own
  planning artefact only when `plan-work-item` picks it up. Cover: the Feature's outcome; a decision
  boundary (in scope / out of scope, stated as explicitly as the in-scope list); an evidence table
  naming any load-bearing claim this Feature rests on with its tier (per
  [`.agents/adrs/README.md`](../../adrs/README.md) — *Evidence tiers*) and what would settle it if it is
  `assumed`; the work-item decomposition (every Story/Spike, its primary slug, and a sentence on what it
  adds); observable proof (how a human confirms the Feature works, positive and negative cases); and a
  completion boundary (what must be true for every item under this Feature to count the Feature done).

Do not add a third file per Epic or per Feature. If you find yourself wanting one, decompose further
instead — a Feature needing its own roadmap is usually two Features.

## 5. Re-running against an existing Epic

Run this skill again **before authorising a new Feature** under an Epic that already has some. Re-read
the Epic (it may have been revised) and the current overview and Feature plans, then:

- Add any Features/Stories/Spikes the updated description now implies that don't exist yet.
- Update the overview and the affected Feature plan(s) to match the current backlog.
- **Do not treat an existing Analysis as a gate.** An unresolved Analysis under this Epic or its
  Features does not block creating the new Feature — flag it in your report to the human, and proceed.
- **New context that doesn't change what a field authoritatively states goes to a comment, not a
  rewrite.** Only regenerate an Epic's or Feature's `Description`/`Acceptance Criteria` when they would
  otherwise be substantively wrong; log everything else (rationale, discussion outcomes, an aside from a
  human) as a comment on the work item. See
  [`azure-devops.md`](../../context/azure-devops.md) → *New context goes to a comment, not into
  Description/AC by default*.

## 6. Report

State: the Feature split you chose and why, the Stories/Spikes under each, every ADO id created, the
estimates set (and confirm `Quotation Points` was touched only on creation), and the paths to the
overview and each Feature plan written or updated. If this is a re-run, state what changed since the
last run.
