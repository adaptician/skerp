Make the human ceremony **repeatable and short**. Your job is assembly, not judgement — the human
adjudicates.

**Target: assembly in a few minutes.** If assembly takes longer, you are analysing instead of assembling.

## 1. Refresh the board

Query the current state of in-flight work items via the Azure DevOps MCP tools, per
[`azure-devops.md`](../../context/azure-devops.md). Remember **the read path is two calls**: `wit_query`
(WIQL) returns ids only, then `wit_work_item` `get_batch` for field values. Update
`.agents/context/current-focus.md` if it has drifted from what the board now shows.

## 2. Assemble, in this order

The order matters: **running code first, prose last.**

### 1 · Proof scripts to run

**The commands, ready to paste.** The human runs or watches them. This is first because it is the only item
that can contradict the others.

For each: what it claims, and **whether it can fail**. A proof that cannot fail is not a proof.

### 2 · Run-log delta

New entries in [`.agents/run-log/`](../../run-log/) since the last checkpoint. Lead with **what
surprised** — that is the part that carries information, and the part a summary tends to smooth away.

### 3 · Assumption-ledger delta

New and changed entries in [`.agents/assumption-ledger/`](../../assumption-ledger/). **Flag every `open`
entry**, with its tier and what would settle it. Call out any that has acquired dependents since it was
raised — an `assumed` claim may not constrain a design.

### 4 · Coherence-review findings awaiting adjudication

Blocking first. Each with its file or claim and the cheapest next probe. **Do not pre-resolve these** — they
exist for the human to decide.

### 5 · Open Blockers by `Severity`

Grouped under their blocked parent, so it is visible which work is actually waiting on a human.

### 6 · `Remaining Work` against `Original Estimate`

Per in-flight item. Name any item where remaining exceeds original — the estimate was wrong, and that is
information, not a failure.

### 7 · Documentation-to-code ratio since the last checkpoint

**The smoke alarm.** Lines of markdown added versus lines of code added, for this period only.

> A rising ratio means the feedback loop is opening again: when running code cannot tell you whether you
> are right, writing more analysis is the only way left to raise confidence. Report the number even when
> it is bad — especially then.

## 3. End with the decisions to be taken

Four options, and the human picks per item: **merge · revert · spike · re-scope.** Plus any toggle flips.

Present each decision with the evidence for it beside it, so the human is not reconstructing context.

## 4. Convert each adjudication into an ADO action

Nothing decided at a checkpoint may live only in the conversation:

| Adjudication | Action |
|---|---|
| Unresolved assumption | → a **Spike**, whose parent Feature the uncertainty generates |
| Accepted coherence finding | → a **work item**, linked to what it concerns |
| Rejected finding | → **a comment on the work item** recording that it was considered and why not |
| Re-scope | → update the AC deliberately **and re-estimate** |

**A decision that abandons work is not complete until the tracker reflects it.**

## 5. Report

State plainly: what was assembled, what the human must decide, and **anything you could not verify.** Do
not soften a bad number, and do not present an unverified claim as settled.
