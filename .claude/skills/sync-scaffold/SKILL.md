Bring the repo into alignment with the Grimoire scaffold, and tell the operator honestly how far
it still has to go. This is assembly and assessment, mostly — the risky decisions (which code
migrates, what gets kept as a deliberate concession) are the human's to make.

## 0. Name which of the three situations this is

- **Fresh solution** — the scaffold is being dropped into a repo with little or nothing in it yet.
  Most checks below will report "absent," and that is expected, not a gap.
- **Scaffold update** — this solution already uses the scaffold; changes made upstream in
  Grimoire-Init need to be pulled in. Diff the incoming governance files (`AGENTS.md`, `.agents/`,
  `.claude/`, `.codex/`) against what changed upstream **deliberately** — do not blindly overwrite.
  Preserve this solution's `.agents/standards/solution/` overlays and anything recorded as a
  concession (§5); those are this solution's own content, not scaffold defaults to clobber.
- **Legacy adoption** — an existing codebase with its own conventions is adopting the scaffold.
  Expect the largest gap in §2–§4, and lean hardest on the non-destructive migration approach.

State which one applies before starting. It changes what counts as an expected absence versus an
actual gap; it does not change which checks run.

## 1. Confirm the Azure DevOps org/project name

**This is the specific failure this step exists to catch:** the scaffold ships with
`.agents/context/azure-devops.md`. If a solution's copy of that file was never updated, agents keep creating work items in
the *scaffold's* project instead of the solution's, and they silently disappear from whoever is
actually watching the right board.

- Read `.agents/context/azure-devops.md`'s frontmatter `verified:` line, and the current alias in
  [`solution-identity.md`](../../../solution-identity.md). If the documented project is still
  literally `Grimoire` while the solution's alias is something else — or anything about it looks
  unconfirmed — treat that as a live mismatch until proven otherwise, not a formality to skip.
- If the `azure-devops` MCP server is connected, call `core_list_projects` (per
  `.agents/context/azure-devops.md`) and confirm the documented org/project actually exists. A
  name that resolves to *a* project is not evidence it is *the* project — the operator confirms
  intent, the tool only confirms existence.
- If the server is not connected, or the right project cannot be confirmed with confidence, **ask
  the operator to state the correct org/project explicitly.** Never silently guess, and never leave
  the scaffold's own default in place on the assumption it is probably fine.
- Once confirmed, update `azure-devops.md`'s `verified:` date and the org/project it names. This is
  a live external fact, not a coding convention — state what you found and what you propose to
  write, and get confirmation before writing it, the same way any other environment-asserting
  change would.

## 2. Assess structural conformance

Walk [`.agents/standards/repository-structure.md`](../../standards/repository-structure.md)
against the actual repo: solution file at root, `src/`, `tests/`, `docs/`, `.build/` (and its
`ci/`, `config/`, environment subfolders), `.editorconfig`, `.mcp.json` + `mcp-servers.md`,
`solution-identity.md`, root `README.md`. For each, record one of: **present and conforming**,
**present but shaped differently**, or **absent**.

This is a structural and governance-file audit, not a line-by-line code-standards review — that
ongoing job belongs to [`conformance-review`](../conformance-review/SKILL.md) on every change
going forward, not a one-shot sweep here. Where code already exists, spot-check the organizing
conventions this scaffold cares about most (Clean Architecture layer boundaries per
`architecture.md`, test-project layout per `testing.md`) rather than attempting full coverage;
where a deeper look is warranted, say so and let a dedicated Analysis or Spike do it.

## 3. Assess planning and governance conformance

Check for `.agents/adrs/`, `.agents/specs/`, `.agents/plans/`, `.agents/run-log/`,
`.agents/assumption-ledger/` (these two have no committed index — if an upstream pull brings back
`.agents/run-log.md` or `.agents/assumption-ledger.md`, do not keep it; `ledgers.mjs --check` fails on
it), and whether any existing planning content matches the depth ladder in [`.agents/specs/README.md`](../../specs/README.md). A legacy repo commonly has its own planning
docs in its own shape (a `docs/planning/` folder, a different spec format) — note where, and how it
diverges.

**Never delete existing planning records to make room for the prescribed structure.** Where the
shape genuinely conflicts, move the existing content into an `_archived/` sibling directory next to
where it currently lives — the same pattern already used for retired skills at
[`.agents/_archived/skills/`](../../_archived/skills/README.md) — with a short README stating what
was archived, when, and why. New planning work then goes into the prescribed structure from that
point forward; the archive stays as the historical record, not as clutter to eventually delete.

## 4. Produce a summary and a migration plan

Report plainly what already conforms, what does not, and — for anything code-level or otherwise
costly to change all at once — a staged plan to close the gap.

- Write the plan as a cross-cutting Plan under `.agents/plans/<slug>.md` per
  [`.agents/plans/README.md`](../../plans/README.md): this work spans the whole repo rather than
  one feature, and "scaffolding a shared library" is that README's own example of what belongs
  here.
- Order stages to front-load reversible, additive moves (archiving misplaced docs, adding missing
  files) before anything that touches working code, minimizing destructive change as far as
  possible — never as a substitute for eventually doing the code-level work, if it's needed.
- **Get explicit human approval before adopting any code-level migration stage.** A scaffold
  adoption is not licence to rewrite a working codebase in one pass — see `agent-workflow.md`'s
  "Align incrementally, don't rewrite."
- If a stage constitutes a significant architectural decision on its own, it may also need an ADR
  — see [`.agents/adrs/README.md`](../../adrs/README.md) for the triggers.

## 5. Record deliberate concessions

When the operator decides a deviation from a root standard is intentional and will stay — not a
gap awaiting migration — document it as an overlay under `.agents/standards/solution/<matching
file>.md`, following the convention already established there: the root standard still applies,
this file states the addition or deviation, and a conflict between the two is resolved in the
solution file's favour and noted in an ADR. Write the ADR too when the concession is significant
enough to be an architectural decision in its own right.

This is not a call to make unilaterally. A concession needs the same explicit sign-off as any other
change to `.agents/standards/**` — see `.agents/owned-by-humans.md`.

## 6. Verify the local environment and integrations

Check that what the repo *declares* is actually *usable*, right now, in this environment:

- **Tool versions** — compare `.node-version`, `global.json`, and `.tool-versions` (per
  [`.agents/standards/tooling.md`](../../standards/tooling.md)) against what is actually installed
  (`node --version`, `fnm current`, `dotnet --version`). Report any mismatch and the fix (typically
  `fnm install` / `fnm use`).
- **MCP servers** — cross-check `.mcp.json` against [`mcp-servers.md`](../../../mcp-servers.md) (per
  [`.agents/standards/mcp.md`](../../standards/mcp.md)) for lockstep, then check which declared
  servers are actually connected and callable in the current session versus merely declared.
- **Connectors and plugins** — the same question applies to anything requiring separate
  authorization outside this session (a Figma connector is the recurring example). If a server or
  connector needs authorization this session cannot grant, say so plainly and name the action the
  operator needs to take — do not guess at credentials or attempt a workaround.
- **Report, do not block on this.** List every gap in one place. This skill is explicitly safe and
  expected to be re-run after the operator addresses some of them — each re-run should show fewer
  gaps, never require starting over.

## 7. Close out

Summarize: which of the three situations this was, what is now in place, and what remains pending
— structural gaps, migration-plan stages awaiting approval, environment gaps — and where each is
tracked (the Plan file, any new ADRs, any solution-overlay files). Do not report anything as
resolved that still depends on a confirmation that has not happened yet: an unconfirmed ADO
project or an unauthenticated connector is a pending item, not a done one.
